# План автоматизации и разработки Telegram-бота для проведения встреч и учета посещаемости

Этот план разработан на основе предоставленного регламента работы в группах (**GURUHLARDA ISHLASH QOIDALARI VA REGLAMENTI**) с учетом требования о **гибком назначении нескольких ролей одному человеку**, а также функционала **предварительного объявления встреч в канале и личном интерфейсе бота**, отметки посещаемости и еженедельной отчетности.

Смежный чек-лист прогресса разработки ведётся в [PLAN.md](./PLAN.md) — обновляй его по мере выполнения этапов, чтобы работу можно было продолжить с того места, где остановились.

---

## 0. Технический стек

* **Backend-фреймворк:** Yii2 (PHP).
* **База данных:** PostgreSQL.
* **Интерфейс бота:** только узбекский язык (все тексты, кнопки, уведомления и отчёты — на узбекском).
* **Масштаб на старте:** одна рабочая группа = один Telegram-канал; бот добавляется в этот канал администратором (права на публикацию постов). Архитектуру БД (`Groups.channel_id`) делать с расчётом на будущее расширение до нескольких каналов/групп, но UI и бизнес-логику первой версии не усложнять поддержкой нескольких каналов одновременно.

## 0.1 Инфраструктура и деплой (важное ограничение)

* **Разработка:** локально через Docker (docker-compose: PHP/Yii2, PostgreSQL, при необходимости nginx). Все docker-конфиги хранить в репозитории.
* **Продакшн-сервер:** хостинг под управлением **Plesk**, доступ к серверу — **только через git** (код появляется в папке после git pull/деплоя). **SSH-консоли и веб-терминала на сервере нет.** Значит, ни `composer install`, ни `php yii migrate`, ни любые другие CLI-команды на проде вручную выполнить нельзя.
* **Установка зависимостей (composer):** через встроенную функцию Plesk «PHP Composer» (кнопка запуска `composer install` в настройках PHP-приложения в панели) — отдельного шага руками не требуется, но нужно проверить, что она доступна на конкретном тарифе.
* **Миграции БД — веб-страница в самом приложении (принципиально, не через Plesk):** заходить в Plesk и искать, куда вставить путь к скрипту, — неудобно для регулярной работы (миграции меняются на протяжении всего проекта, не разово). Поэтому делаем `SystemController::actionMigrate` — защищённая паролем/ролью админа страница внутри бот-приложения (например `https://.../system/migrate`), которая программно выполняет `Yii::$app->runAction('migrate/up', ['interactive' => 0])` и показывает результат на экране. Обновил код через git → зашёл на один и тот же URL → нажал кнопку — миграции применились. Никакого обращения к панели Plesk каждый раз.
* **Планировщик задач Plesk (подтверждено, есть на тарифе):** «Сайты и домены → Планировщик задач → Запланировать задачу» (`panel1.eskiz.uz/smb/scheduler/add-task`). Тип задачи **«Выполнить PHP-скрипт»** — путь к PHP-файлу, аргументы, версия PHP (доступны версии вплоть до **PHP 8.5** — для Yii2 подходит). Используется **только** для того единственного, что реально должно выполняться по расписанию само по себе:
  * **Еженедельный субботний отчёт (единственная регулярная крон-задача в MVP):** консольная команда `console/controllers/CronController::actionWeeklyReport()`, задача Plesk на субботу, окно расчёта 9:30–10:00, публикация в 10:00. Настраивается один раз при деплое и дальше не трогается — в этом отличие от миграций, которые меняются часто.
  * **Публикация итогов встречи в канал:** не крон — часть синхронного флоу, вызывается напрямую из веб-контроллера бота сразу после того, как Секретарь/Модератор завершили отметку присутствия.
* **Отложено на будущее (не входит в MVP):** личные напоминания участникам за 1 час и за 15 минут до встречи (Модуль 2) — требуют частого крона (каждые 5–15 мин), который пока не заводим. Можно вернуться к этому позже — тогда проверить, какой мин. шаг расписания поддерживает планировщик Plesk (сейчас видели только «Ежедневно» в примере).
* **Приём апдейтов от Telegram:** **вебхук** (не long polling) — Telegram сам стучится на HTTPS-эндпоинт бота при каждом апдейте, постоянный процесс не нужен. Контроллер `BotController`, действие `actionWebhook`.
* **Веб-панель администратора (логин/пароль):** `/site/login` (креды из `.env`: `ADMIN_LOGIN`/`ADMIN_PASSWORD`, без отдельной таблицы в БД — админ один). После входа — верхняя навигация: **Foydalanuvchilar** (все зарегистрированные пользователи), **Guruhlar** (список групп + создание новой группы + переход к участникам), **Uchrashuvlar** (все встречи и их статус), **Migratsiyalar** (та же кнопка `migrate/up`, но через логин, а не токен в URL). На странице группы — добавление участников (из уже зарегистрированных через `/start` пользователей) и назначение Модератора.
* **Структура контроллеров:**
  * `BotController::actionWebhook` (web) — приём апдейтов Telegram (POST от Telegram).
  * `SiteController` — `actionLogin`/`actionLogout` (вход в админку), `actionIndex` (редирект на логин/панель).
  * `AdminController` (web, только для залогиненного админа) — `actionUsers`, `actionGroups`, `actionGroupCreate`, `actionGroupMembers`, `actionGroupAddMember`, `actionGroupSetModerator`, `actionMeetings`, `actionMigrate`.
  * `SystemController::actionMigrate` (web, по токену) — альтернативный запуск миграций без логина, для автоматизации/CI.
  * `console/controllers/CronController::actionWeeklyReport()` — единственная регулярная задача, запускается планировщиком Plesk как PHP-скрипт по субботам.

## 1. Общее описание системы

Бот предназначен для полной автоматизации организации встреч рабочей группы:
* Публикация анонсов встреч в привязанном Telegram-канале.
* Отображение списка запланированных встреч и деталей в личном меню бота для участников.
* Назначение нескольких ролей одному пользователю на конкретную встречу.
* Учет посещаемости Секретарем/Модератором.
* Автоматическая публикация итогов сразу после встречи и еженедельная субботняя аналитика.

### Основные сущности и ролевая модель (из Регламента)
* **Модератор (Moderator):** Назначает роли, создает встречи, задает тему, формат (offline/online) и время встреч (не менее чем за 24 часа или за 12 часов при срочности).
* **Секретарь (Kotib):** Проводит перекличку/отметку участников встречи.
* **Дополнительные роли:** Эксперт процесса (Jarayon eksperti), Технический сотрудник (Texnik xodim), Докладчик (Taqdimotchi).
* 💡 **Совмещение ролей:** Один пользователь может выполнять одновременно **несколько ролей** на конкретной встрече (например: *Kotib + Texnik xodim*).

## 2. Архитектура и основные модули бота

### Модуль 1. Регистрация и управление группами
* **Регистрация пользователей:** Участники регистрируются в боте (ФИО, должность/отдел) через `/start`.
* **Формирование групп — только через веб-админку (не через бот):** создание группы, привязка Telegram-канала, добавление участников в группу и назначение Модератора выполняет **администратор в веб-панели** (`/admin/groups`, `/admin/group-members`). Самостоятельное создание группы или вступление в неё через бота отключено — пользователь просто регистрируется (`/start`), а дальше администратор вручную добавляет его в нужную группу.
* **Назначение ролей:**
  * **Модератор** назначается администратором один раз для группы (кнопка «Moderator qilish» на странице участников группы).
  * Остальные роли (**Kotib**, **Jarayon eksperti**, **Texnik xodim**, **Taqdimotchi**) назначает Модератор — но **не под конкретную встречу, а на уровне группы**, как шаблон (кнопка «👥 Guruh a'zolari» в боте: тап на участника → toggle-клавиатура ролей). Один человек может иметь несколько ролей одновременно.
  * **Роли встречи = роли группы на момент её создания.** Отдельного шага «выбрать участников и роли» при создании встречи **нет** — все участники группы автоматически становятся участниками встречи с ролями из своего группового шаблона. Если роль человеку нужно поменять — это делается через «👥 Guruh a'zolari» (и это действует на все будущие встречи), а не через мастер создания встречи.
  * **Базовая роль «Ishtirokchi» (участник):** назначается автоматически всем, у кого нет ни одной специальной роли в шаблоне группы — чтобы человек никогда не отображался с пустым списком ролей.

### Модуль 2. Планирование и АНОНС встреч (Объявления)
* **Интерфейс создания встречи (в боте, только для Модератора группы):**
  * Мастер из 3 шагов: тема → дата/время → формат (`Offline` / `Online`) → встреча тут же создаётся и публикуется.
  * **Участники и роли не выбираются вручную** — берутся автоматически из состава группы и её ролевого шаблона (см. Модуль 1).
  * Дата/время выбирается **inline-календарём** (кнопки на ближайшие 14 дней, затем кнопки часов) — свободный текстовый ввод остаётся резервным вариантом («✏️ Boshqa sana/vaqt»), т.к. не все пользователи технически подкованы и жёсткий текстовый формат вызывал постоянные отказы при вводе.
  * Встречу нельзя создать позже чем за 12 часов до её начала (регламент, упрощённый с исходного 24ч/12ч-при-срочности). Для тестовых пользователей (`.env: TEST_BYPASS_TELEGRAM_IDS`) это ограничение отключается.
  * Модератор может **отменить** встречу — статус `cancelled`, сохраняется в БД, пропадает из активных списков.
* **Меню бота зависит от роли пользователя в группе:** обычный участник — 2 кнопки (Uchrashuvlar, Guruh — только просмотр), Kotib — 3 (+ Davomat), Модератор — 4 (+ Yangi uchrashuv, Davomat). Davomat доступен только Модератору и Kotib.

* **📣 1. Объявление в привязанном Telegram-канале:**
  Сразу после создания встречи (или за 24ч / 12ч согласно регламенту) бот автоматически публикует анонс в канал группы:
  > 📢 **ОБЪЯВЛЕНИЕ О ПРЕДСТОЯЩЕЙ ВСТРЕЧЕ!**  
  > 👥 **Группа:** {Название группы}  
  > 📌 **Тема:** «{Тема встречи}»  
  > 📅 **Дата и время:** {Дата, Время}  
  > 📍 **Формат:** {Offline / Online}  
  > 
  > 🎭 **Распределение ролей на встречу:**  
  > • 👑 **Модератор:** {ФИО}  
  > • 📝 **Секретарь:** {ФИО}  
  > • 💡 **Эксперт процесса:** {ФИО}  
  > • 🛠 **Технический сотрудник:** {ФИО}  
  > • 🎤 **Докладчик:** {ФИО}  
  > *(Примечание: один человек может выполнять несколько ролей)*

* **📅 2. Отображение встреч в ЛИЧНОМ меню бота (для участников):**
  У любого участника группы в самом боте есть кнопка **«📅 Предстоящие встречи»**:
  * При нажатии бот выводит список запланированных встреч с датой, временем, темой и ролью, которая назначена именно этому пользователю.
  * ~~Бот присылает личное напоминание участникам за 1 час и за 15 минут до начала встречи.~~ *(отложено на будущее, не входит в MVP — см. раздел 0.1)*

### Модуль 3. Проведение встречи и учет посещаемости
* **Запуск встречи:** В назначенное время бот отправляет Модератору и Секретарю сообщение с кнопками для фиксации присутствия.
* **Логика отметки (Согласно п. 2.3.1 и 2.3.2 Регламента):**
  * Ответственный выбирает статус по каждому участнику:
    * ✅ **Пришел**
    * ❌ **Не пришел (Отсутствовал)**
    * ⚠️ **Отсутствовал с разрешения / по уважительной причине** *(Фиксируется пропуск в соответствии с п. 2.3.2)*.
    * *(При присутствии менее половины времени встречи — отмечается "Не пришел" по п. 2.3.1)*.

### Модуль 4. Публикация итогов встречи в канал
* После завершения отметки бот публикует в Telegram-канал отчет:
  > 📢 **Итоги встречи по теме:** «{Тема встречи}»  
  > 📅 **Дата и время:** {Дата, Время}  
  > 
  > ✅ **Присутствовали:**  
  > • {ФИО} — *{Роль 1, Роль 2}*  
  > • {ФИО} — *{Роль}*  
  > 
  > ❌ **Не пришли:**  
  > • {ФИО} — *{Роль}*  

### Модуль 5. Еженедельная субботняя отчетность
* **Автоматический планировщик (Каждую субботу):** отчёт формируется (расчёт данных) в промежутке с 9:30 до 10:00, публикация в канал — ровно в 10:00.
* Бот подводит итоги недели в канале:
  > 📊 **Еженедельный отчет по посещаемости:**  
  > 🔹 **Всего встреч за неделю:** {Количество}  
  > ✅ **Всего визитов (Пришли):** {Кол-во} раз  
  > ❌ **Всего пропусков (Не пришли):** {Кол-во} раз  
  > 
  > 📈 **Детализация по участникам:**  
  > • {ФИО}: ✅ {X} пришел / ❌ {Y} пропустил  
  > • {ФИО}: ✅ {X} пришел / ❌ {Y} пропустил

## 3. Пошаговый план разработки (Roadmap)

### Этап 1. База данных и логика ролей
1. Структура БД: таблицы `Users`, `Groups`, `Meetings`, `Meeting_User_Roles` (многие-ко-многим для совмещения ролей), `Attendance`.

### Этап 2. Модуль объявлений и личного интерфейса
1. Разработка команды/меню **«📅 Предстоящие встречи»** в боте для каждого участника.
2. Интеграция авто-постинга анонса о создании встречи в Telegram-канал группы.
3. Система персональных уведомлений участников через бота.

### Этап 3. Учет посещаемости и публичные отчеты
1. Интерактивная клавиатура для Секретаря/Модератора для быстрой отметки присутствующих.
2. Автоматическая форматированная публикация итогов встречи в канал.
3. Настройка Cron-задачи для автоматической субботней рассылки итогового отчета.

### Этап 4. Тестирование и запуск
1. Проверка полного цикла: *Создание встречи -> Публикация анонса в канал -> Просмотр встречи в боте -> Проведение встречи и отметка -> Публикация итогов -> Субботний сводный отчет*.
2. Передача готового бота.
